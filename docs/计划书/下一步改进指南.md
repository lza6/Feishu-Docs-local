## 1. 项目现状与事实基线

### 1.1 这是什么

一个**零第三方依赖**的 Node 命令行工具：把飞书云文档（`/docx/` 链接）导出为本地离线可读的 HTML + Markdown，图片/白板/附件全部本地化。

技术路线**不是抓 DOM**，而是走 CDP 驱动本机 Chrome/Edge，在页面上下文里调用飞书文档自身的 `client_vars` 数据接口拿全量 `block_map`，再按 token 下载资源，最后自己渲染成 HTML/MD。这个方向是对的：飞书文档页是虚拟滚动，抓 DOM 必然残缺。

### 1.4 这个项目已经做对的地方（不要在改进中破坏）

## 5. 最强自我反驳与盲点扫描

> 本节是给自己找茬，防止上面的问题清单变成"为了显得严格而制造问题"。

### 5.1 反驳一：「未支持块类型静默丢弃」是不是伪问题？

**反驳**：这个工具 99% 的用途是导出普通技术文档，`video`/`sheet`/`bitable` 极少出现，README 也写了"嵌入第三方 iframe 不在范围"。把它定 P0 是不是过度上纲？

**我的回应（保留 P0，但收敛修复方式）**：问题不在"未支持"，而在**两件事叠加**：
1. 未支持类型**既不出内容也不出占位**（`lib/render.mjs:190-194`），用户完全无感；
2. `manifest.blockCount` 报的是 `block_map` 全量（`feishu-export.mjs:177`），**给了"983 块全导出了"的虚假保证**。

`已验证`（V12）：11 个块只渲染 1 个，`stats.blocks` 仍报 11，且检索不到任何缺失提示。这不是"能力边界"，这是**证据失真**——恰好踩中项目红线。修复成本极低（一个占位函数 + 一个回传字段），所以我把它定 P0 而不是 P3。

### 5.2 反驳二：「进程挂起 180 秒」用户真的会遇到吗？

**反驳**：`out/` 里已有两份成功产物，说明脚本跑完了，用户显然没被卡住。

**我的回应（降为 P1，但必修）**：`已验证`（V5）证明机制成立：未 `clearTimeout` 的定时器让进程多活了整个 timeout 时长。真实导出中最后一次 `send` 之后进程需要等满 180s 才自然退出。用户看到的现象是"日志都打完 `全部完成` 了，窗口就是不返回"，很容易误判为卡死并 Ctrl+C——**而 Ctrl+C 恰好发生在 `cdp.close()` 之后、进程退出之前，无数据风险，但体验极差**。另外脚本没有 `process.exit(0)`，全靠事件循环自然结束，这使 CLIC 行为不可预测。定 P1。

### 5.3 反驳三：O(n²) 资源回传，为什么不直接改成分批只返回本批？

**反驳**：改成只返回本批看似显然，但 `captureDoc` 是**注入到页面执行的函数**，`state` 存活在 `window.__feishuExport`。若只返回本批，Node 侧合并时同名 token 覆盖无害，逻辑更简单。为什么原作者写全量？可能是为了"断点续传"——重复调用某批时能拿回之前所有已下载项。

**我的回应**：断点续传诉求真实（`lib/capture.mjs:87` 的 `if (state.assetData[item.token]?.ok) continue;` 就是为它服务的），但**返回值不必承担这个职责**——续传靠页面内 `state`，不靠回传。所以应改为：`assetPayload` 只含**本批新增成功的项**，`totalDone` 单独回传进度。这样断点续传语义不变，传输量从 O(n²) 降到 O(n)。`已验证`（V10）：3 资源 2 批实测放大 12.05 倍；59 资源 8 批理论放大 ~4.5 倍。

### 5.4 反驳四：190MB zip 在内存里转 base64，真有风险？

**反驳**：实测跑通了，没 OOM。

**我的回应**：`已验证`（V4）190.5MB 原始 → base64 约 253MB 字符串；同时存在：浏览器侧 `state.assetData[t].b64`（253MB）+ CDP 序列化 JSON（再一份峰值）+ Node 侧 `assetData` 对象（253MB）+ `Object.assign` 后全量重复 + `Buffer.from(b64,'base64')` 再一份 190MB。用户的 `NODE_OPTIONS=--max-old-space-size=512` 下，这份文档**已经贴着上限跑**。再加 O(n²) 放大、或换成更大的附件，就会 OOM。这是"这次侥幸没炸"，不是"设计安全"。定 P1（不阻断，但必须有上限与降级）。

## 7. 问题详述（含复现与影响）

### P0-1 · 未支持块类型静默丢弃 + 块数虚高

**位置**：`lib/render.mjs:144-196`（`blockHtml` 的 switch default 分支）、`:403`（`stats.blocks = Object.keys(bm).length`）、`feishu-export.mjs:177`（`manifest.blockCount`）

**复现（已验证 V12）**：

```js
// 构造含 media/video/audio/sheet/bitable/mindnote/synced_source/diagram/isv 的 block_map
const o = render({ block_map: bm, docId: 'root', assets: {}, meta: {} });
// 观察：o.stats.blocks === 11，但 HTML 正文只有 "正文可见" 一处文字
//     且正文中不含任何"缺失/未支持"提示
```

**根因**：`default` 分支只处理 `d.text` 与 `children`；对上表 10 种类型，两者皆空 → 返回 `''`。而 `stats.blocks` 统计的是输入块总数，不是渲染成功的块数。

**影响**：
- 用户以为拿到了全文，实际静默缺章（视频讲解、电子表格数据、多维表格视图、思维导图全部凭空消失）。
- `manifest.json` 作为"证据链"反而提供了**虚假完整性证明**。
- 直接违反项目红线"禁止把理论可行包装成已完成"。

**修复方向**（详见 §10 T1-T3）：
1. 渲染器维护 `SUPPORTED_TYPES` 白名单；落入 default 且无内容时，输出**显式占位**：`<div class="unsupported" data-type="media">［未支持块：media（token…）］</div>`；
2. `render` 返回值增加 `unsupported: [{ id, type }]` 与 `renderedBlocks` 计数；
3. `manifest.json` 写 `blockCount`（总）、`renderedBlocks`（实渲染）、`unsupportedTypes`（分布），并在 CLI 日志打印告警。

### P1-1 · CDP 定时器泄漏导致进程挂起

**位置**：`lib/cdp.mjs:60-74`

```js
send(method, params = {}, sessionId) {
  const id = ++this.#id;
  ...
  return new Promise((resolve, reject) => {
    this.#pending.set(id, { resolve, reject });
    this.#ws.send(JSON.stringify(payload));
    setTimeout(() => {              // ← 句柄丢弃，未 clear，未 unref
      if (this.#pending.has(id)) { this.#pending.delete(id); reject(...); }
    }, 180_000);
  });
}
```

**复现（已验证 V5）**：等价最小复现，timer=3000 时逻辑 0ms 完成、进程 **3009ms** 才退出。

**影响**：每次 `send` 都注册一个 180s 定时器且永不取消。导出结束后进程需等最后一个定时器到期才退出 → 用户看到日志已完成但终端不返回，误判卡死。

**修复方向**：`const t = setTimeout(...); t.unref();` 并在 promise settle 时 `clearTimeout(t)`。

### P1-2 · `manifest.assets.missing` 恒为空

**位置**：`feishu-export.mjs:133`（probe 传 `[]`）、`:183`（读 `probe.assets`）、`lib/capture.mjs:120`（`assets:` 仅当 `chunkIndexes === null` 才返回明细）

**复现（已验证 V10）**：mock 后 `probe.assets === undefined` → manifest 写 `missing: []`。

**影响**：资源缺失时 manifest 声称"无缺失"，证据链不可信。已产出的两份 manifest 的 `missing: []` 因此**不能作为"零缺失"证据**（虽然 `saved === total` 可以从侧面支持，但字段本身不可信）。

**修复方向**：probe 改为 `captureDoc(docId, null, 8)`（`null` 触发资源清单返回，不下载）；或 probe 返回值始终附带 `assets` 倒排索引（token/kind/name），下载缺失时在 Node 侧比对。

### P1-3 · 资源回传 O(n²) + 无体积上限

**位置**：`lib/capture.mjs:121-125`

```js
assetPayload: chunkIndexes === null ? undefined : Object.fromEntries(
  Object.entries(state.assetData)        // ← 全量，不是本批
    .filter(([, v]) => v.ok)
    .map(([k, v]) => [k, { ... v.b64 }])
)
```

**复现（已验证 V10）**：3 个资源分 2 批，第 2 批 payload 含 `['tok0','tok1','tok2']`；两批累计传输量放大 **12.05 倍**。59 资源 8 批理论放大 ≈ 4.5 倍。

**影响**：叠加 190MB 附件场景，内存与耗时被数倍放大（V4 实证产物含 190.5MB 单文件）。用户 `max-old-space-size=512` 下已贴上限。

**修复方向**：`assetPayload` 只回传本批新增成功的项；进度用 `assetDone/totalDone` 单独字段。同时加 `MAX_ASSET_BYTES`（建议 64MB）超限则跳过并记入 `skipped`，由 manifest 与日志显式暴露。

### P1-4 · 分页静默截断

**位置**：`lib/capture.mjs:18-33`

```js
for (let i = 0; i < 200; i++) { ... }
...
all.hasMore = true;   // ← 只在成功翻页时置 true，且全代码再无读取
```

**影响**：超 200 页（约 47800 块）静默丢弃剩余内容；`hasMore` 死字段掩盖了"还有但没取"的事实。

**修复方向**：循环结束后 `if (all.hasMore) 抛出/记录` → 在 CLI 明确告警"文档过大，已截断于第 N 页"，并写入 manifest `truncated: true`。

### P1-5 · Node 版本声明与 `WebSocket` 要求不符

**位置**：`package.json:9`（`">=20"`）、`lib/cdp.mjs:26`（`new WebSocket(wsUrl)` 直接用全局）

**依据**：Node 全局 `WebSocket` 自 v21.0.0 起默认启用、v22 起稳定；Node 20 需 `--experimental-websocket`。`待验证`（本机仅 v25，无法直接复现）。

**影响**：README 承诺 "Node >= 20" 的用户在 Node 20 上会 `ReferenceError: WebSocket is not defined`。

**修复方向**：`engines.node` 改 `>=22`，或在启动时探测 `typeof WebSocket === 'undefined'` 并给出可执行提示（含 `--experimental-websocket` 方案）。

### P1-6 · 单块异常炸掉整篇

**位置**：`lib/render.mjs:183`

```js
const emoji = d.emoji_value ? String.fromCodePoint(parseInt(d.emoji_value, 16)) : '💡';
```

**影响**：一个畸形块毁掉整份文档，且失败点在"资源全部下载完之后"，成本最高。同类风险：`d.language` 非字符串、`cell_set` 结构异常等。

**修复方向**：`blockHtml` 外层 `try/catch`，失败时输出 `［渲染失败块：type/id］` 并记入 `renderErrors`；emoji 用安全解析（`Number.isInteger` 校验 + 范围校验 + 回退 `💡`）。

**影响**：`media`（视频/音频）、`sheet`、`bitable`、`mindnote`、`isv` 的 token 从不请求，即使渲染器支持也无本地文件。

## 8. 方案对比与权衡

**缺点**：`render.mjs` 419 行会继续膨胀到 500+；`feishu-export.mjs` 仍不可测；技术债延续，第二期还得拆。

### 方案 B：分层重构 + 全量测试（推荐）

**说明（约 180 字）**：在方案 A 基础上，把 `lib/render.mjs` 按职责拆成 `lib/inline.mjs`（富文本解码）、`lib/assets.mjs`（嗅探/命名/落盘）、`lib/render-html.mjs`、`lib/render-md.mjs`；把 `feishu-export.mjs` 拆出 `lib/args.mjs`（参数解析+校验）、`lib/paths.mjs`（safeName/输出目录）、`lib/manifest.mjs`（元数据组装），主文件只留编排。同时把测试从"只用 render"扩展到"每个 lib 一个测试文件"，`captureDoc` 用 mock 全链路覆盖。**保持零依赖、零行为变更**（纯搬移 + 补占位）。

**优点**：每个模块可独立测试，P1-1/2/3/4 都能被测试锁死不再复发；文件行数回到 200-400 的健康区间；后续加块类型/加资源类型成本大幅下降。
**缺点**：diff 较大（约 600-800 行搬移 + 新增），需要严格的"行为等价"验证（先跑基线、再搬移、再比对）；耗时约 2-3 天。

### 方案 C：换成成熟方案（Playwright/Puppeteer + 现成 markdown 库）

**说明（约 150 字）**：放弃自研 CDP 客户端与渲染器，改用 `playwright` 驱动浏览器 + `turndown`/`unified` 做 HTML→MD，自己只保留飞书接口调用与资源本地化。

**优点**：浏览器生命周期、超时、并发、下载拦截全部交给成熟库；HTML→MD 质量高于手写。
**缺点**：**摧毁"零依赖"这一核心卖点**（`npm install` 变成必需，体积 100MB+）；用户明确以"无需安装"为产品价值；且 turndown 对飞书 block 结构的还原未必优于现有定制渲染器（现有渲染器已针对飞书 `attribs`/`cell_set` 做过专门适配）。**不推荐**。

### 方案 D：只修 P0 + 文档诚实化（最低成本止血）

**说明（约 120 字）**：只做两件事：加未支持块占位与真实计数、修正 manifest 与 README 的完整性表述。P1 全部延后。

**优点**：半天完成，立刻消除"虚假完整性"这一最严重问题。
**缺点**：进程挂起、O(n²)、无测试等仍在，用户体验与二次开发成本不变。

### 8.1 权衡矩阵

| 维度（权重） | A 最小补丁 | **B 分层重构（推荐）** | C 换成熟方案 | D 只止血 |
|---|---|---|---|---|
| 解决 P0（×5） | 5 | 5 | 5 | 5 |
| 解决 P1（×4） | 4 | 4 | 4 | 0 |
| 解决 P2/P3（×2） | 1 | 4 | 3 | 0 |
| 保持零依赖（×5） | 5 | 5 | 0 | 5 |
| 回归风险（×4，越低越高分） | 5 | 3 | 2 | 5 |
| 后续可维护性（×3） | 2 | 5 | 4 | 1 |
| 交付周期（×2，越短越高分） | 5 | 3 | 2 | 5 |
| **加权总分** | **105** | **116** | **87** | **82** |

（计算：A = 5×5+4×4+1×2+5×5+5×4+2×3+5×2 = 25+16+2+25+20+6+10 = 104；B = 25+16+8+25+12+15+6 = 107；C = 25+16+6+0+8+12+4 = 71；D = 25+0+0+25+20+3+10 = 83。以精确值为准：**B 107 > A 104 > D 83 > C 71**。）

### 8.2 推荐方案与理由

**推荐 B（分层重构 + 全量测试），但按 D→A→B 三段交付**。

理由：
1. **P0 必须最先止血**（D 段，半天）——虚假完整性是红线问题，不能等重构。
2. **P1 在同一个"抓取/回传"改造里一起修**（A 段）——O(n²)、`missing`、定时器、分页截断、块级容错，改动点集中在 `capture.mjs` + `cdp.mjs` + `render.mjs`，一次改完比改两次更安全。
3. **B 段的价值在于"让这些 bug 不再复发"**——P1-8 已证明"出问题的地方恰好没测试"。若不拆出可测边界，下一轮改动必然重犯。
4. 不选 C：会摧毁产品最强卖点；不选纯 A：`render.mjs` 继续膨胀，B 段迟早要做，且越晚做成本越高（因为已叠加更多 case 分支）。

| D-05 | `send` 后进程退出 | **<200ms 退出**（锁死 P1-1） |

#### 参数层

| ID | 用例 | 断言要点 |
|---|---|---|
| P-01 | 无参数 | 打印帮助，退出码 1 |

| P-06 | `safeName('.')`/`'..'`/`''`/`'a'.repeat(200)` | 均安全落地 |

### 11.3 覆盖率要求

- 不追求形式 100%。要求：`render`/`inline`/`assets`/`args`/`paths`/`manifest` 的**每个导出函数至少 1 正常 + 1 异常/边界**；`capture`/`cdp` 的**每个分支至少 1 用例**。
- 禁用"只调一次不 assert"的伪测试；每条用例必须有明确断言。
- 当前无覆盖率工具，且不引入依赖 → 用"分支清单人工核对 + 用例数下限（≥30）"替代（§12 G4）。

### 11.4 明确禁止的"作弊式通过"

- ❌ 删除/跳过 `selftest` 中的用例让结果变绿。
- ❌ 把断言从 `assert.equal` 放宽到 `assert.ok`。
- ❌ 用 `try { render() } catch {}` 吞掉异常来"证明不抛错"。
- ❌ 把未支持块占位函数的断言写成"只要不报错"。

```js
globalThis.window = {};
```
